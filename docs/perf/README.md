# Performance harness

Everything about performance in OpenSheets lives here: the budgets, the numbers, and the gate.

```
docs/perf/budgets.json    every budget in PLAN.md §10.6, plus the id each one is measured under
docs/perf/baseline.json   the numbers the gate compares against. Committed. Changed deliberately.
docs/perf/latest.json     the last run. Regenerated by Scripts/bench.sh; commit it or don't.
Scripts/bench.sh          run the lane, write latest.json, fail on a regression
.github/workflows/perf.yml  the same thing, on macos-26, on every push to main
```

```bash
Scripts/bench.sh                    # measure and gate
Scripts/bench.sh --no-compare       # measure only
Scripts/bench.sh --record-baseline  # measure, then replace the baseline (idle machines only)
Scripts/bench.sh --help
```

---

## The one thing to know

**Counts and byte sizes are exact. Wall-clock numbers are not, and how not depends entirely on
how many times you measured.**

That is not a slogan, it is a measurement. The same suite, four back-to-back runs on the Wave 1
development machine at 1.3–1.6× its core count in load:

| metric | unit | spread across four runs |
| --- | --- | --- |
| `model.cellstore.window50x50.allocations` | count | **0.0%** |
| `model.diff.100k.visited` | count | **0.0%** |
| `model.runlength.runs` | count | **0.0%** |
| `model.cellstore.rss.1m.bytes` | bytes | **0.3%** |
| `model.cellstore.sparse.100k.bytes` | bytes | 0.5% |
| `model.runlength.geometry.10k.seconds` | seconds | 1.0% |
| `model.cellstore.build.1m.seconds` | seconds | 1.7% |
| `model.diff.100k.seconds` | seconds | 1.7% |
| `model.a1.parse.1m.seconds` | seconds | 5.1% |
| `model.cellstore.sparseScan.seconds` | seconds | 12.7% |

Those timing numbers are only that tight because every one of them is a **minimum over many
runs**. Measured *once* per run instead — which is how they started out — the same three metrics
spread by **127%, 167% and 182%** at 2.5–3× load. Nothing about the code changed; only the
iteration count did. If you add a timing metric and it moves 20% between runs, raise its
`iterations` before you raise the tolerance.

Two things stayed noisy for reasons worth knowing:

- `model.cellstore.sparseScan.seconds` at 12.7%, because it walks 100,000 addresses scattered
  across a million rows and is therefore bound by the memory system, which is what the other six
  agents' compilers are also using.
- `model.cellstore.sparse.100k.bytes` is an RSS *delta*, which is page-granular. It is declared
  `"noisy": true` in `budgets.json`, which moves it to the timing tolerance.

So the gate uses two tolerances, both in `budgets.json`:

- **10%** for counts and byte sizes. They do not move.
- **20%** for wall-clock metrics and anything flagged `noisy`, widened by 2.5× when the machine's
  load average exceeds its core count — and when that happens the run says so, loudly, and tells
  you to re-check idle.

**Write your budget as a count wherever the question allows it.** "The recalculation visited 9,800
cells" is a better assertion than "the recalculation took 180 ms": it is exact, it is the same on
every machine, and when it fails it names the bug. A duration tells you something is slow; a
visited-set size tells you *why*.

## Adding a metric

One call, from any test target that can import `TestSupport`:

```swift
import TestSupport

@Suite("XLSXReaderBenchmarks", .serialized, .enabled(if: Benchmark.isEnabled))
struct XLSXReaderBenchmarks {
    @Test("opening a 100k-cell workbook")
    func open100k() throws {
        let data = try FixtureLibrary.data("perf/100k-cells.xlsx")

        // Timing: min of N, budget-checked, load-aware. Prints a summary line either way.
        PerfGuard.expect("xlsx.open.100k.firstPaint.seconds", budget: .milliseconds(800),
                         iterations: 5) {
            _ = try? XLSXReader().read(data)
        }

        // Work done: exact, and the number that will still mean something in six months.
        let filesystem = FailingFileSystem()
        _ = try XLSXReader(filesystem: filesystem).read(data)
        PerfGuard.expectWork("xlsx.open.100k.inflatedEntries", value: Double(filesystem.count(of: .read)),
                             atMost: 8, unit: .count,
                             note: "a reader that inflates every entry rather than the parts it parses")
    }
}
```

Three rules:

1. **The suite name must contain `Benchmark`.** `bench.sh` runs `swift test --filter Benchmark`,
   which is what keeps a million-cell build out of everybody else's `swift test`.
2. **Gate it on `Benchmark.isEnabled`** (`OPENSHEETS_BENCH=1`), for the same reason.
3. **Add the id to `budgets.json`.** An id that is emitted but not declared still appears in
   `latest.json`, flagged `[undeclared]` — but only a declared id shows up as `blocked` when
   *nobody* emits it, and that is the line that stops a budget quietly disappearing.

Ids are a contract: `baseline.json` is keyed on them, so renaming one drops the metric from the
comparison rather than failing. Add a new id and retire the old one.

`Benchmark.record(id:value:unit:budget:note:)` is the low-level form if neither wrapper fits.

## Profiling

The three questions worth asking, and the tool for each.

### Where is the time going — Time Profiler

The benchmark bundle can be launched directly, which is what Instruments needs:

```bash
cd Packages/OpenSheetsCore
swift build -c release --build-tests -Xswiftc -enable-testing

BIN="$(swift build -c release --show-bin-path)"
BUNDLE="$BIN/OpenSheetsCorePackageTests.xctest/Contents/MacOS/OpenSheetsCorePackageTests"
HELPER="$(dirname "$(xcrun --find swift)")/../libexec/swift/pm/swiftpm-testing-helper"
FRAMEWORKS="$(xcode-select -p)/Platforms/MacOSX.platform/Developer/Library/Frameworks"

OPENSHEETS_BENCH=1 DYLD_FRAMEWORK_PATH="$FRAMEWORKS" \
xcrun xctrace record \
  --template 'Time Profiler' \
  --output ~/Desktop/opensheets.trace \
  --launch -- "$HELPER" \
      --test-bundle-path "$BUNDLE" \
      --testing-library swift-testing \
      --filter 'millionCells' \
      --no-parallel

open ~/Desktop/opensheets.trace
```

The `--filter` matters: profile one benchmark, not the suite. A trace of twenty benchmarks is a
trace of the harness.

Without Instruments, `sample` is often enough and needs no setup:

```bash
Scripts/bench.sh --no-compare &          # or run the suite however you like
sample OpenSheetsCorePackageTests 10 -f ~/Desktop/sample.txt
```

### Where is the memory going — Allocations

Same command, `--template 'Allocations'`. Two settings in the UI earn their keep: **Record
reference counts** (finds retain/release traffic, which on this codebase is usually a value type
that grew a class inside it) and **Generation marks** around the operation, which turns "the
process is big" into "this call allocated 41 MB and kept it".

Cheaper, and usually sufficient:

```swift
let (workbook, report) = WorkCounters.measuringAllocations { try reader.read(data) }
print(report)   // "128034 blocks, 41.2 MB, RSS 43.1 MB"
```

`WorkCounters.residentBytes()` and `peakResidentBytes()` are the numbers PLAN.md §10.6's 600 MB
ceiling is about. Peak is the honest one: a reader that briefly holds two copies is over budget
even if it frees one before anybody looks.

Both read **process-wide** counters. `bench.sh` runs `--no-parallel` for that reason — measured
once with suites in parallel, a 500-allocation delta came back *negative*, because another suite
freed more than this one allocated in the same window.

### Where are the syscalls going — File Activity, or just count them

```swift
let filesystem = FailingFileSystem()
_ = try subject.save(workbook, to: url, filesystem: filesystem)
#expect(filesystem.count(of: .write) == 1)      // more than one means a re-encode
#expect(filesystem.count(of: .rename) == 1)     // the atomic replace, once
print(filesystem.summary)                        // "rename=1 stat=3 sync=2 write=1"
```

That is a better test than `--template 'File Activity'` for anything you can express as a count,
and it runs in CI.

## Updating the baseline

The baseline is a **claim about the code**, not a record of the machine. Replacing it because the
gate went red is how a gate stops meaning anything.

Before you touch it, answer: *did the code get slower, or did the machine?*

```bash
# 1. Quiet the machine. Really quiet: no builds, no other agents, no Xcode indexing.
uptime          # load average should be well under the core count

# 2. Measure without gating, twice, and check the two runs agree.
Scripts/bench.sh --no-compare && cp docs/perf/latest.json /tmp/run1.json
Scripts/bench.sh --no-compare && diff <(jq -S .metrics /tmp/run1.json) <(jq -S .metrics docs/perf/latest.json)

# 3. Compare strictly — no widening for load, because there is none.
Scripts/bench.sh --strict

# 4. Only if the regression is real and intended:
Scripts/bench.sh --record-baseline
```

`--record-baseline` **refuses to run** above 0.5× load. A baseline taken on a busy machine bakes
that contention into every future comparison, and every run afterwards looks like an improvement.

If the machine genuinely cannot get quieter — seven agents sharing one Mac was the Wave 1 reality —
`--baseline-on-a-busy-machine` records anyway, sets `"baselineTakenUnderLoad": true` in the file,
and says so. The long name is the point: it should be a decision, not a habit. Re-record on a
quiet machine at the first opportunity; a timing number taken under contention is a ceiling, not
a measurement.

Commit `baseline.json` on its own, with a message that says *why the numbers moved*:

> perf: rebaseline after switching CellStore to a run-length row index
>
> model.cellstore.build.1m.seconds 71 ms → 88 ms (+24%), deliberate: the index costs
> more to build and pays for itself in model.cellstore.sparseScan.seconds, 13 ms → 4 ms.
> Every other metric unchanged. Measured at 0.11× load.

A rebaseline commit that only says "update perf baseline" is indistinguishable from someone
silencing a real regression, and six months later nobody can tell which it was.

CI can do it too: run the **Performance** workflow with **record_baseline** checked, download the
artifact, and commit `baseline.json` from it. That is the right route when the regression only
appears on the runner.

## The baseline that is committed today

`baseline.json` was recorded at **1.94× load**, with `--baseline-on-a-busy-machine`, and carries
`"baselineTakenUnderLoad": true` and a `note` saying so. Seven agents shared this Mac for the whole
of Wave 1 and it never went below 1.2× — a poller ran for twenty minutes waiting for 0.5× and never
saw it.

It is usable: every timing value is a minimum over 5–50 runs, and the four verification runs after
it was taken agreed with it to within 1.7% on all but one metric. But it is a **ceiling**, not a
measurement. **Re-record it on a genuinely idle machine at the first opportunity** — one command,
and the numbers can only get better:

```bash
Scripts/bench.sh --record-baseline
```

## Reading `latest.json`

```jsonc
{
  "configuration": "release",
  "revision": "…",                    // from OPENSHEETS_PERF_REVISION or GITHUB_SHA
  "machine": { "cores": 12, "normalizedLoad": 0.54, … },
  "calibrationSeconds": 0.001471,     // the divisor — see below
  "metrics": {
    "model.diff.100k.seconds": {
      "value": 0.0139, "unit": "seconds", "budget": 1.0,
      "status": "measured",           // measured · degraded · blocked
      "samples": 12,                  // the value is the minimum of these
      "owner": "A7"
    }
  }
}
```

`status` is the honest bit:

- **measured** — taken on a machine quiet enough for the number to mean something.
- **degraded** — taken while the machine was loaded. Still recorded, still compared, but the
  in-test assertion was waived and said so.
- **blocked** — declared in `budgets.json`, emitted by nobody. The code it measures does not exist
  yet. It stays in the report so the budget cannot quietly vanish.

`calibrationSeconds` is a fixed CPU kernel — no allocation, no syscalls, fixed instruction count —
timed on whatever machine ran the suite. `bench.sh` divides every seconds-valued metric by this
run's value over the baseline's, so a laptop and a CI runner can be compared. Counts and byte
sizes are *not* normalised: they are machine-independent, and scaling them would hide real growth.

## When the gate goes red

1. **A count or byte regression is real.** Those moved 0.3% across five runs at 3× load. Read the
   metric's `description` in `budgets.json` — most of them name the bug outright ("a diff that
   walks the rectangle rather than the populated rows costs this many visits").
2. **A timing regression on a loaded machine is not evidence.** The run tells you the load. Re-run
   idle with `--strict` before acting.
3. **A timing regression on an idle machine, twice, is real.** Profile it: `--template 'Time
   Profiler'`, `--filter` the one benchmark.
4. **If it is a deliberate trade,** rebaseline and say why. See above.

## Known limitations

- **The `blocked` list is most of PLAN.md §10.6.** Opening an xlsx, scrolling a grid, recalculating
  a dependency graph and diffing a watched file are all measured by code that does not exist yet.
  Their budgets and metric ids are declared and waiting; the owning agent emits the id and the
  number appears. Nothing in the harness changes.
- **`WorkCounters` reads process-wide statistics.** Serial runs only. `bench.sh` handles it;
  a benchmark run any other way must not trust an allocation delta.
- **`mstats().chunks_used` counts blocks still held, not blocks made.** Work that allocates a
  million temporaries and frees them reads as zero. Right for "does this retain per cell", wrong
  for "how much churn does this cause" — use Instruments' Allocations for that.
- **`TestSupport` links Swift Testing, so only test targets may link it.** A plain executable that
  imports it builds and then dies at launch with `Library not loaded: @rpath/Testing.framework`.
- **`--record-baseline` will not run above 0.5× load**, by design.
  `--baseline-on-a-busy-machine` overrides it and stamps `baselineTakenUnderLoad` into the file.
