The premise

Don't out-feature Excel. Out-sync it.

People pirate Excel at home because work accounts block AI plugins, then bolt on weak third-party assistants. But the strongest spreadsheet agent already exists — Claude Code. It just has no good surface. It can already read and write files; what it lacks is a viewer that stays in sync and a structured way to touch a workbook without corrupting it.

So the bet is narrow and deliberate: visualisation and sync fidelity are the product. Depth comes from Claude. We build fast, gorgeous rendering, honest editing, and a watertight file-watch loop. We don't build a charting engine, pivot authoring, or all 500 Excel functions — and we never execute a macro.

The core loop · PLAN.md §1.2

The reason the app exists

Everything else is in service of these five steps. If this loop is flawless, the app is good. If it's flaky, nothing else matters.

01 · Open

Grid paints

A 100k-cell workbook is on screen in under 800 ms. The sidebar shows the workspace path and MCP status.

02 · Delegate

Claude edits the file

You run claude in that folder. It writes through plain file tools — or, better, our MCP tools.

03 · Notice

The pill rises

Watcher fires. A glass capsule appears: Changed on disk · 1 sheet, 42 cells · Refresh ⌘R.

04 · Review

Pill morphs into a diff

Per-sheet counts and a scrollable cell list — D2 120 → 129.6. You accept, inspect, or discard.

05 · Verify

Changed cells flash accent, then fade over six seconds. Snapshots let you rewind if the agent got it wrong.

Architecture · PLAN.md §2

Xcode-thin, SwiftPM-heavy

Eleven agents editing one project.pbxproj produces unmergeable garbage. So ~95% of the code lives in SwiftPM targets, where adding a file requires editing no manifest. The Xcode app target is created once and is effectively read-only until the final wave. This is the single most important structural decision for parallel work.

Why AppKit for the grid, SwiftUI for everything else

SwiftUI cannot draw a million cells at 120 fps; there is no honest way around that. The grid is a custom NSView in an NSScrollView, drawing with Core Graphics, virtualised to the visible rect. All chrome is SwiftUI so it can use real Liquid Glass. That split is deliberate.

Visual direction · PLAN.md §3

Quiet Glass

The failure mode of a glass UI is that everything floats and nothing is readable. A spreadsheet is 90% dense text, so the discipline has to be severe.

One opaque plane — the grid. Glass floats above it, never behind data. Grid surfaces are solid tokens, never materials.
TierAPISurfacesRule
Chrome .glassEffect(.regular) toolbar, formula bar, sheet tabs, sidebar Edge-anchored; grid bleeds under via backgroundExtensionEffect
Floating .regular.interactive() stats pill, refresh pill, ⌘K palette, inspector Detached, shadowed, capsule or 24pt continuous
Signal .regular.tint(_) conflict banner, error, "Claude changed this" Tint is semantic — amber = conflict, accent = agent, red = error

The detail that separates real glass from blurry rectangles

Every cluster of two or more glass elements lives inside a GlassEffectContainer, so adjacent controls merge into a single lens instead of stacking independent blurs. Stacked glass is the number-one tell of a fake, and A5 ships a lint test that fails the build when the rule is broken.

Beyond that: system accent colour rather than a hardcoded blue, tabular figures in every cell without exception, springs-only motion, and the grid scroll never animated — it has to be 1:1 with the trackpad or it feels broken. Light and dark are both defined explicitly from day one, and reduceTransparency swaps every glass surface for a solid token, live, without relaunch.

Known risks · stated up front

Three hard problems

xlsx writing destroys things

A naive writer silently eats charts, pivots, and conditional formats — the classic failure of every open-source spreadsheet tool.

Surgical ZIP rewriting: re-emit only the XML parts we actually modelled, pass every other entry through byte-identical. Tested per-entry, not by whole-file hash.

A formula engine is months of work

Implementing Excel's function library and evaluation semantics properly is not a v0.1 task.

xlsx already stores the cached result beside every formula, so v0.1 renders a correct workbook with zero evaluation. We only evaluate what someone edits — and flag what we can't compute rather than guessing.

"Touch any file" needs a boundary

A spreadsheet is untrusted input. A cell can contain text aimed squarely at an agent, and the MCP server inherits your full file access.

Workspace grants: the server physically cannot read or write outside folders you approved in the app, with a deny-list that overrides every grant. 25+ escape tests; any escape blocks release.

The rules that keep seven agents from colliding

Own your files, touch nothing else. SheetModel is frozen after Wave 0 — needed changes go in a request log, not into the type. Nobody touches project.pbxproj. Wave 1 agents never depend on each other's output; they build against protocols and A7's fakes. Ship green: swift build && swift test passes, strict-concurrency warnings are errors, and an honest throw notImplemented beats a silent wrong answer.

Rollout

v0.1 Viewer — open, render, navigate, watch → diff → refresh, snapshots. v0.2 Editor — editing, formulas, formats, undo, atomic save, conflict resolution. v0.3 Claude — MCP server, workspace grants, activity feed. v0.4 Polish — sort, filter, find/replace, inspector, charts view-only.

Unfinished work ships dark behind Flags rather than blocking a release. Distribution is a notarised DMG on GitHub Releases plus a Homebrew cask. No telemetry by default — this is an app for people who left the cloud on purpose.
